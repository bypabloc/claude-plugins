# 0.4.1 — Un commit en segundo plano pide su hash

- **Fecha**: 2026-11-19 · **Commit**: `24b7785` · **Tipo**: fix
- **Visto en**: klinikae, lote 161 (commit de docs de 161.7)

## Síntoma

La sesión hizo un `git commit` con `run_in_background`. No hubo `commit.remind`, el hash nuevo nunca llegó a
`Done` y `Stop` soltó tres veces por `external-wait` sin pedirlo.

## Causa

`PostToolUse` llega cuando el Bash en segundo plano arranca, antes de que exista el commit. Sin hash en la salida,
el plugin caía en `git log -1`, que devolvía el HEAD anterior, ya anotado: no había nada que pedir.

## Cambio

- Si el Bash del commit lleva `run_in_background`, se guarda el directorio y el HEAD del arranque
  (`backgroundCommits`, hasta 5) y no se usa `git log -1`.
- El siguiente commit, mensaje o `Stop` busca los commits propios de la rama desde ese HEAD
  (`git log --first-parent --no-merges base..HEAD`) y los suma a los pendientes. Un merge de `dev` no trae
  commits ajenos.

## Prueba

`a git commit in a background Bash asks for its own hash once it lands, not the old HEAD`
(`hooks/register.test.ts`).

## Lección

En un hook de herramienta, «terminó la llamada» no es «terminó el trabajo» cuando la herramienta corre en segundo
plano.
